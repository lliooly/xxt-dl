# 全仓库可靠性审计与修复设计

## 背景

XXT DL 当前的类型检查、31 项既有测试和生产构建均能通过，但这些结果尚未覆盖新增的刷题模块、真实 API 路由契约和任务生命周期边界。只读审计已经确认以下风险：

1. 下载任务服务用业务状态代替真实运行锁。任务已发出 `done` 或 `error` 状态、Playwright 尚未完全退出时，新任务可能提前启动，并与旧任务争用 `.xxt-profile/` 或 `output/`。
2. 题库 API 会把输出目录读取失败、JSON 解析失败和空题库统一返回为成功的空结果，前端无法区分正常空状态与接口异常。
3. 刷题模块存在填空题无法作答、中文填空答案归一化错误、切题后选项状态残留、错题重练读取旧来源和错题计数不及时刷新等已确认问题。
4. 新增模块缺少针对并发、输入边界和状态转换的自动化测试；部分文件的错误处理、命名和代码布局不一致。

本轮不承诺发现理论上所有未知缺陷，而是以全量静态审查、可复现测试、生产构建和本地浏览器验证为证据，修复当前仓库内能够确认的问题，并记录无法离线验证的剩余风险。

## 目标

- 修正下载、选课、停止、状态查询和题库读取 API 的契约与错误语义。
- 确保同一时间最多只有一个 Playwright 下载任务占用浏览器 profile 和输出目录。
- 让重复启动、重复选课、停止中的请求和任务完成后的立即重启具有确定行为。
- 修复已确认的刷题判题与界面状态问题。
- 审查采集、解析、CLI、Web、刷题和导出代码中的异常吞噬、空值、边界条件、重复逻辑与风格差异。
- 为每项行为修复补充先失败、后通过的回归测试。
- 保持 CLI、现有导出格式和本地 Web 主流程兼容。

## 非目标

- 不使用真实用户账号自动访问学习通，也不上传课程内容。
- 不绕过验证码、权限控制或隐藏答案。
- 不引入 SQLite、云同步、Telegram Bot 或 AI 能力。
- 不进行与缺陷无关的模块迁移或大规模 UI 重写。
- 不把缺少统一格式化工具扩大为依赖升级或全仓库机械重排。

## 方案选择

### 方案 A：可靠性优先的定向全量审计（采用）

保留现有模块边界，对 API 契约、任务锁、刷题状态和审计发现的其他根因做小步修复。每项业务行为先建立失败测试，再修改最少生产代码。该方案能覆盖用户关心的 API、锁竞态和代码质量，同时把回归风险控制在可验证范围内。

### 方案 B：显式状态机和 reducer 重构

将下载服务与刷题界面重写为统一状态机。长期结构可能更清晰，但改动跨越 Playwright、Route Handler 和多个 React 组件；缺少真实学习通环境时，无法为这种规模的重写提供相称验证。

### 方案 C：仅修接口表面症状

只修改 API 路径、响应或前端请求。改动较小，但无法解决任务资源释放竞态、错误吞噬和刷题模块中的已确认问题，不符合本轮审计目标。

## 详细设计

### API 契约

下载接口继续使用以下路径：

- `POST /api/download/start`
- `POST /api/download/course`
- `POST /api/download/stop`
- `GET /api/download/state`
- `GET /api/practice-chapters`

下载接口保持 `{ state }` 成功响应和 `{ error }` 失败响应，避免无必要的前端迁移。输入校验统一放在 `src/web/download-api.ts`，业务状态错误由任务服务提供稳定错误码，再映射为 HTTP 状态码。

题库接口需要区分 3 种情况：

- 输出目录不存在或没有题库文件：返回 HTTP 200 和空题库，这是正常首次使用状态。
- 单个题库文件损坏或结构无效：返回非 2xx 响应和可操作错误信息，不再静默跳过。
- 目录或文件系统出现其他读取错误：返回 HTTP 500，不向客户端泄露敏感绝对路径。

前端加载器验证响应结构。非 2xx、无效 JSON 或字段类型不匹配都进入可见错误状态，旧数据必须清空，避免显示过期题库。

### 下载任务互斥与状态转换

`activeJob` 是否存在是任务资源锁的唯一依据。只要旧任务的 `run()` 尚未进入 `finally` 并释放，`start()` 就返回冲突；不能因为快照已经是 `done`、`error` 或 `stopped` 而提前放行。

任务生命周期如下：

```text
start
  -> 创建任务 ID 和 starting 快照
  -> 创建任务对象并占用 activeJob
  -> 执行 run
  -> done / error / stopped 仅更新对外快照
  -> run finally 完成后释放 activeJob
  -> 允许下一个 start
```

所有异步回调继续按任务 ID 隔离，旧任务不能覆盖新任务快照。服务在调用 `run()` 前先保存 `activeJob`，避免任务同步回调或同步失败形成无锁窗口。

课程选择需要原子地从 `selecting-course` 进入后续状态。第一个有效选择被接受后，后续重复选择返回明确状态错误，不能成功但不执行。停止操作在关闭浏览器期间继续持有运行锁；只有 `run()` 完成清理后才允许重启。

### 刷题可靠性

沿用已有的刷题模式可靠性设计，并纳入本轮统一验证：

- 选择题和文本题使用不同答案归一化规则，文本题保留 Unicode 文字和数字。
- 填空题或无选项题显示受控文本输入及提交按钮。
- 单选、多选和文本草稿按章节 ID 与题号组成的题目身份重置。
- 单选组件始终保持受控，不在字符串与 `undefined` 之间切换。
- 错题模式每次「再来一轮」都读取最新错题本；空集合不创建无效会话。
- 仪表盘错题数由父组件显式刷新，不依赖组件恰好重新挂载。

### 全量代码审查规则

按以下顺序审查所有生产源码与测试：

1. 数据正确性：解析、判题、链接筛选、文件名和输出内容。
2. 状态与并发：共享可变状态、Promise 生命周期、取消、重复请求和资源释放。
3. 错误处理：异常吞噬、错误状态码、过期状态和用户可操作提示。
4. 输入边界：未知 JSON、空字符串、非法数字、损坏文件和数组越界。
5. 一致性：命名、类型出口、导入顺序、注释风格和重复辅助函数。

仅修复有代码证据或失败测试支持的问题。纯审美差异只在本次涉及的文件内整理，避免制造大面积无意义 diff。

### 测试策略

新增或扩展以下测试：

- API 输入、响应映射、题库文件发现、损坏 JSON 和结构校验。
- 下载任务同步启动失败、运行锁、完成清理窗口、错误清理窗口、重复选课和停止竞态。
- 刷题中文填空、多选集合比较、会话导航、最新错题重建和空会话。
- 静态审查发现的其他边界问题，各自使用最小失败用例复现。

组件行为优先提取可测试的纯逻辑；不为测试而大规模改写 UI。浏览器验证覆盖下载 API 初始状态、无题库、损坏题库错误展示、填空题、连续单选题切换和错题重练。

## 验收标准

- 已确认的 API、任务锁和刷题问题均有根因说明及回归测试。
- 全量源码审查完成，发现的问题已修复或在最终报告中说明无法离线验证的原因。
- `npm run check`、`npm test` 和 `npm run build` 均以退出码 0 完成。
- 本地浏览器主要流程没有控制台错误或错误的接口状态。
- 不修改或提交用户已有的 `next-env.d.ts` 改动。
- 不提交 `.xxt-profile/`、`output/`、`release/` 或个人课程资料。

## 风险与约束

- 学习通页面结构和线上行为无法在没有真实账号与课程数据时完整验证；相关结论只基于静态分析、模拟对象和已有选择器规则。
- Next.js 开发或构建命令可能自动改写 `next-env.d.ts`。该文件视为用户已有改动，始终从本轮提交范围排除。
- 浏览器 profile 是独占资源。测试使用模拟下载任务，不直接打开或修改用户的 `.xxt-profile/`。
